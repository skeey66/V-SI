# V-SI · SP2 LLM 에이전트 설계

작성일: 2026-09-18
상태: 설계 완료 · 구현 전
범위: SP2 (실제 LLM 에이전트 + MCP 도구 서버). SP1 스펙은 `2026-09-17-a2a-kernel-design.md`.

## 1. 배경과 목표

SP1은 LLM을 한 번도 부르지 않고 오케스트레이션 전 구간을 검증했다. 에이전트 4종은 YAML을
읽어 결과를 내놓는 스텁이었고, 그래서 환류·재시도·크래시 복구를 결정적으로 시험할 수 있었다.

SP2는 그 스텁 자리에 **실제 LLM과 실제 도구**를 넣는다. 증명 대상은 바뀌지 않는다 —
에이전트 인프라와 분산 시스템 설계다. 생성된 코드의 우수성이 아니라, **비결정적인 에이전트가
섞여도 SP1에서 만든 구조가 버티는지**를 보인다.

### SP2가 달성해야 할 것

요구사항 하나가 실제 LLM 네 기를 거쳐 사람 개입 없이 종단 상태에 도달한다. 검증은 모델
의견이 아니라 **실제 실행 결과**(pytest·Bandit 종료코드)에 근거하고, 생성된 코드는 격리된
컨테이너를 벗어나지 못한다.

`escalated`로 끝나는 것도 성공이다. 8b 로컬 모델이 문제를 못 푸는 일은 흔하고, 그때 상한이
정확히 돌아 실행이 유한하게 끝나는 것이 이 설계가 작동한다는 증거다. **완주를 성공의 조건으로
두면 모델 운에 완료 정의를 맡기는 것이 된다.**

## 2. 범위

### 포함 (SP2)

- `LlmExecutor` — LLM 대화 루프와 MCP 클라이언트를 도는 A2A 실행기
- MCP 도구 서버 — 파일 연산, `pytest`, `bandit` 을 표준 프로토콜로 노출
- 워크스페이스 컨테이너 — 생성 코드의 실행 격리
- 기획 에이전트의 **인수 테스트 생성** — 요구사항을 기계가 검사할 수 있게 만든다
- 도구 호출 이벤트 — 그래프 UI 에 에이전트의 현재 동작 표시
- 상한·타임아웃 재조정 (`run_s` 배선 포함)

### 제외

| 항목 | 이유 | 이관 |
|---|---|---|
| 사람 승인 게이트(`input-required`) 구현 | SP2 는 "LLM 을 꽂고 환류가 실제로 돈다"에 집중 | SP3 |
| 대시보드 지표, 단일 vs 다중 에이전트 비교 실험 | 측정은 시스템이 돈 뒤 | SP3 |
| 외부 LLM API (Claude, OpenAI) | 비용 0원 유지. 어댑터 경계는 두되 구현하지 않는다 | 필요 시 |
| 요구사항마다 컨테이너 생성 | Docker 소켓 마운트의 보안·복잡도 대비 이득이 작다 | 범위 밖 |
| 멀티 요구사항 동시 실행 최적화 | 단일 Ollama 인스턴스가 병목. 동시 1~2건으로 제한 | SP3 |

## 3. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| LLM 런타임 | Ollama (호스트) | 비용 0원. 컨테이너에서 `host.docker.internal:11434` |
| 모델 (네 역할 전부) | `qwen3:8b` | 도구 호출이 정확하고, 측정상 가장 빠르며, 단일 모델이라 축출이 없다 |
| 도구 프로토콜 | MCP Python SDK, Streamable HTTP | 에이전트가 별도 컨테이너라 stdio 를 쓸 수 없다 |
| 테스트 실행 | `pytest` | 기획이 쓰는 인수 테스트의 형식 |
| 보안 검사 | `bandit` | 종료코드가 판정이 된다 |

SP1 의 스택(FastAPI · `a2a-sdk` 1.1.2 · PostgreSQL · OpenTelemetry · React)은 그대로다.

### 모델 선정 근거 (실측)

도구 2개(`write_file`, `run_tests`)를 주고 "파일을 쓰고 테스트를 실행하라"고 지시했다.
세 후보 모두 **순서와 인자가 올바른 도구 호출 2개**를 냈다. 도구 호출 능력은 변별점이 아니었다.
갈린 것은 속도다.

| 모델 | 웜 응답 시간 | 도구 호출 |
|---|---|---|
| `qwen3:8b` | **12.3초 · 12.2초 · 14.5초** | 정확 |
| `qwen3:4b` | 69.8초 · 76.3초 | 정확 |
| `qwen3-4b-nothink` | 78.8초 · 109.4초 | 정확 |

**작은 모델이 더 느렸다.** 5~6배 차이다. 직관에 반하지만 반복 측정에서 일관됐고,
`nothink` 변종도 마찬가지여서 thinking 출력량 때문이 아니다. 원인은 규명하지 않았다 —
설계 판단에 필요한 것은 원인이 아니라 순위다.

`gemma3:4b` 는 도구 호출을 공식 지원하지 않아 제외했다. `exaone3.5:7.8b` 는 검증하지 않았다.

### 단일 모델을 쓰는 이유

측정 중 8b 가 27.7초 걸린 경우가 있었다. 다른 모델을 돌리는 사이 메모리에서 축출됐다가
다시 로드된 것이다. **모델을 두 종류 쓰면 에이전트가 번갈아 호출할 때마다 축출과 재로드가
반복된다** — 재로드 비용이 15~100초라 추론 시간보다 크다.

역할별로 모델을 나누면 얻을 게 있을 것 같지만, 이 하드웨어에서는 정반대다. 네 역할 모두
`qwen3:8b` 를 쓴다. 항상 웜 상태이고, QA 와 보안이 병렬로 호출해도 같은 로드된 모델을 공유한다.

### 시간 예산의 근거

**이 12~15초가 이 설계의 모든 시간 상수를 결정한다.** 도구 루프는 한 턴으로 끝나지 않으므로
에이전트 작업 하나가 60~90초, 환류까지 가는 요구사항 하나가 5~10분이다. SP1 은 1초였다.

## 4. 아키텍처

### 4.1 교체 지점은 하나다

SP1 이 이음매를 만들어 두었다.

```
create_agent_app(card, executor, task_store)
                       ↑
        StubExecutor  ←→  LlmExecutor
```

`AgentExecutor.execute(context, event_queue)` 를 구현하는 클래스를 바꾸는 것이 SP2 의
전부다. A2A 서버, AgentCard, 푸시 알림, Task 저장소는 **한 줄도 바뀌지 않는다.**

모드는 `VSI_AGENT_MODE=stub|llm` 환경변수로 고른다. 같은 이미지가 둘 다 담는다 —
스텁을 지우지 않는 이유는 §12 에 있다.

### 4.2 서비스 구성

```
┌─ 기본 네트워크 ─────────────────────────────────┐
│  orchestrator  event-gateway  jaeger  web       │
│  planner  dev  qa  security ──→ host:11434      │
└──────────────┬──────────────────────────────────┘
               │ (에이전트만 양쪽에 속한다)
┌──────────────┴─ internal 네트워크 (인터넷 없음) ─┐
│  workspace ── MCP 서버 + 생성 코드 실행          │
└──────────────────────────────────────────────────┘
```

`workspace` 는 인터넷에 나갈 수 없다. 생성된 코드가 외부로 데이터를 보내거나 패키지를 받아오는
경로가 **네트워크 수준에서** 없다. 호스트 파일시스템 마운트도 없다.

상태기계, 아웃박스, 리컨실러의 구조, 이벤트 게이트웨이, DB 스키마는 그대로다. 오케스트레이터에서
바뀌는 것은 시간 상수, `run_s` 배선(§9), 그리고 **디스패치 페이로드**(§4.3) 셋이다.

### 4.3 디스패치 페이로드를 넓힌다

SP1 의 오케스트레이터는 에이전트에게 `{"requirement_id": ...}` 만 보낸다. 스텁은 그것으로
충분했다 — 할 일이 YAML 에 있었기 때문이다.

LLM 에이전트는 그것으로 일할 수 없다. 무엇을 만들어야 하는지, 몇 회차인지, **직전 회차가 왜
반려됐는지**를 알아야 한다. 완료 기준 4(§13)가 요구하는 "환류가 실제 실패 출력에 근거한다"는
이 페이로드 없이는 성립하지 않는다.

```json
{
  "requirement_id": "REQ-1",
  "title": "정수 두 개를 더하는 계산기",
  "revision": 2,
  "feedback": [
    {"agent": "qa", "verdict": "FAIL",
     "summary": "test_add_negative: assert add(-1, -1) == -2, 실제 0"},
    {"agent": "security", "verdict": "PASS", "summary": ""}
  ]
}
```

`feedback` 은 직전 회차 검증자들의 `test_report`·`security_report` 아티팩트에서 만든다.
1회차에는 빈 배열이다.

**에이전트가 오케스트레이터의 워크플로 테이블을 읽지 않는 것이 요점이다.** 필요한 맥락은
A2A 메시지가 실어 나른다. 에이전트의 DB 접근은 SP1 과 동일하게 `DatabaseTaskStore` 와
§8.1 의 자문 이벤트 쓰기로만 한정된다 — 작업 지시를 DB 조회로 얻기 시작하면 A2A 메시지가
의미를 잃고, 에이전트를 다른 머신에 둘 수 없게 된다.

## 5. 에이전트 내부 구조

### 5.1 루프

```
execute(context, event_queue)
  ├ 시스템 프롬프트(역할별) + 작업 지시 + 이전 회차 피드백(있으면)
  ├ MCP 세션 열기 — 헤더에 requirement_id·revision·agent
  └ 반복 (최대 12턴, 최대 600초)
       ├ POST host:11434/api/chat  (tools = 역할별 도구 목록)
       ├ tool_calls 없음 → 최종 산출물 확정 → 종료
       └ tool_calls 있음 → MCP 호출 → 결과를 대화에 append → 계속
```

턴 상한이나 시간 예산을 넘기면 **에이전트가 스스로 작업을 실패로 끝낸다.** 새로운 종료 규칙을
만들지 않는다 — 실패한 작업은 SP1 의 재시도·환류 상한이 이어받는다.

### 5.2 역할별 구성

네 역할 모두 `qwen3:8b` 를 쓴다(§3). 다른 것은 도구 권한과 프롬프트다.

| 역할 | 도구 | 산출물(`kind`) | 판정 |
|---|---|---|---|
| 기획 | `write_file` | `requirements` | 없음 |
| 개발 | `list_files` `read_file` `write_file` | `source_code` | 없음 |
| QA | `list_files` `read_file` `run_tests` | `test_report` | **pytest 종료코드** |
| 보안 | `list_files` `read_file` `run_security_scan` | `security_report` | **bandit 종료코드** |

기획의 `requirements` 아티팩트는 **명세와 인수 테스트를 함께** 담는다(§7). 워크스페이스에
`test_*.py` 로 쓰인 내용이 그대로 아티팩트 스냅샷에 들어가므로, 개발이 무엇을 목표로 받았는지가
DB 에 남는다.

### 5.3 판정은 모델이 내리지 않는다

QA 의 `verdict` 는 `run_tests` 의 종료코드가 결정한다. 0이면 PASS, 아니면 FAIL 이다.
LLM 의 역할은 실패 출력을 개발이 고칠 수 있는 문장으로 옮기는 것뿐이다.

**코드에 LLM 이 판정을 뒤집을 경로가 없어야 한다.** `verdict` 는 도구 결과에서 직접 읽고,
모델 응답 텍스트는 `test_report` 의 설명 필드로만 들어간다. 이것을 테스트로 고정한다(§12).

모델이 도구를 한 번도 부르지 않고 끝나면 판정할 근거가 없다 — 그 작업은 **실패**다.
PASS 도 FAIL 도 아니다. 근거 없는 통과를 만드느니 재시도하게 둔다.

### 5.4 개발은 테스트를 돌리지 못한다

`run_tests` 를 개발에게 주지 않는다. 주면 성공률은 오르지만 검증 권한이 개발에게 생겨 QA 가
형식이 된다. 역할 분리가 이 설계의 요점이므로 권한도 분리한다.

> **되돌림 조건.** 개발이 인수 테스트를 통과시키는 비율이 너무 낮아 환류가 거의 항상
> 상한까지 가면, 개발에게 `run_tests` 를 주는 쪽이 낫다. 그때는 QA 의 역할을 "돌린다"에서
> "왜 틀렸는지 설명한다"로 다시 정의하고, 판정 권한은 여전히 QA 에 둔다.

## 6. MCP 도구 서버와 워크스페이스

### 6.1 경로 봉쇄

**LLM 은 워크스페이스 루트를 모른다.** 도구 인자에 `requirement_id` 를 받지 않는다. MCP
세션이 열릴 때 에이전트가 헤더로 넘긴 값으로 서버가 루트를 정하고, 모델은 그 아래 상대경로만
쓴다. 모델이 다른 요구사항의 디렉터리를 가리킬 방법 자체가 없다.

모든 경로는 `Path.resolve()` 후 루트 하위인지 검사한다. 아니면 도구 **오류 결과**를 돌려준다 —
예외를 던지지 않는다. 모델이 그 오류를 보고 고칠 수 있어야 하기 때문이다.

막아야 하는 것: 상위 탈출(`../`), 절대경로(`/etc/passwd`), 루트 밖을 가리키는 심볼릭 링크.
세 가지 모두 테스트로 고정한다.

### 6.2 도구 명세

| 도구 | 인자 | 반환 |
|---|---|---|
| `list_files` | 없음 | 상대경로 목록 |
| `read_file` | `path` | 파일 내용 (최대 32KB, 초과 시 절단 표시) |
| `write_file` | `path`, `content` | 성공 여부, 바이트 수 |
| `run_tests` | 없음 | `exit_code`, `stdout` 꼬리, `stderr` 꼬리 |
| `run_security_scan` | 없음 | `exit_code`, `stdout` 꼬리, `stderr` 꼬리 |

`pytest` · `bandit` 은 서브프로세스 타임아웃 60초를 건다. 출력은 각 4KB 로 절단한다 —
보안이 아니라 **모델 컨텍스트 보호**다. 8b 모델의 컨텍스트에 pytest 전체 출력을 넣으면
지시가 묻힌다. 절단은 꼬리를 남긴다(실패 요약이 끝에 있다).

### 6.3 파일시스템과 DB 의 역할

워크스페이스는 **작업대**이고, 불변 기록은 DB 에 남는다.

회차마다 디렉터리를 새로 파지 않는다. 개발은 제자리에서 고친다. 대신 작업이 끝날 때마다 파일
내용을 SP1 의 `artifacts` 테이블에 스냅샷으로 넣는다 — `producer_task` 가 그 회차의 Task 행을
가리키고, `version` 이 올라간다.

"3회차 개발이 무엇을 냈는가"는 파일시스템이 아니라 DB 가 답한다. **SP1 의 불변 행 모델이
그대로 유지된다.**

## 7. 기획이 인수 테스트를 쓴다

SP2 에서 가장 중요한 설계 결정이다.

기획 에이전트의 산출물은 둘이다 — 요구사항 명세와, 그것을 검사하는 `test_*.py`.

이것이 세 가지를 동시에 해결한다.

1. **개발의 목표가 모호하지 않다.** 함수 이름·시그니처·기대값이 테스트에 박혀 있다. 8b 모델이
   자유 서술형 요구사항에서 API 를 상상해내지 않아도 된다.
2. **환류 피드백이 사실이 된다.** "이 테스트가 이 줄에서 이 값을 기대했는데 저 값이 왔다"는
   실행 결과지 모델 의견이 아니다.
3. **검증자가 똑똑할 필요가 없다.** QA 는 돌리기만 한다.

기획이 쓴 테스트가 틀릴 수 있다. 통과 불가능한 테스트를 쓰면 개발이 환류 상한까지 가고
`escalated` 로 끝난다. **이것은 버그가 아니라 관측 결과다** — 어느 단계가 실패의 원인인지
계보(`revision_of`)와 아티팩트 스냅샷에 남는다. SP3 의 비교 실험이 바로 이런 데이터를 쓴다.

## 8. 데이터 모델 변경

SP1 의 5개 테이블은 그대로다. 추가 컬럼도 없다. 바뀌는 것은 **`events` 테이블의 writer 가
둘이 된다**는 점이다.

### 8.1 에이전트가 쓰는 이벤트

```
tool_called  { agent, tool, revision, args_summary }
tool_result  { agent, tool, revision, exit_code?, ok }
```

에이전트가 자기 DB 세션으로 직접 쓴다. 오케스트레이터를 거치지 않는다.

> **불변식.** 에이전트가 쓰는 이벤트는 **자문(advisory)** 이다. 워크플로 권위가 없다.
> UI 리듀서도 리컨실러도 이 이벤트에서 상태를 **유도해서는 안 된다**. 상태의 근거는 언제나
> 오케스트레이터가 상태 전이와 한 트랜잭션에 쓴 `state_changed` 다.
>
> 이 규칙을 깨면 트랜잭셔널 아웃박스의 보장이 무너진다 — 에이전트의 이벤트 쓰기는 워크플로
> 전이와 원자적이지 않으므로, 이벤트는 있는데 상태는 안 바뀐 창이 존재한다.

## 9. 상한과 타임아웃

### 9.1 `submit` 은 블로킹이 아니다

`a2a_client.submit()` 은 `return_immediately` 를 세우므로 Task 생성 즉시 돌아온다. 에이전트가
5분을 돌아도 오케스트레이터는 기다리지 않는다. 따라서 `tool_s`(30초)·`executor_s`(5분)는
**손댈 필요가 없다.**

### 9.2 층

| 층 | SP1 | SP2 | 집행 주체 |
|---|---|---|---|
| 에이전트 턴 상한 | — | **12턴** | `LlmExecutor` |
| 에이전트 작업 예산 | — | **600초** | `LlmExecutor` |
| `tool_s` | 30초 | 30초 | `engine.dispatch_agent` |
| `executor_s` | 300초 | 300초 | httpx 클라이언트 |
| `stale_after_s` | 5초 | 5초 | 리컨실러 |
| `stuck_after_s` | 60초 | **900초** | 리컨실러 |
| `step_s` | 900초 | 900초 (미배선) | — |
| `run_s` | 3600초 (미배선) | **3600초 (배선)** | 리컨실러 |

**안쪽 상한은 행동할 수 있는 쪽이 집행한다.** 에이전트는 자기가 예산을 넘긴 것을 알고 스스로
실패로 끝낼 수 있다. 그래서 `stuck_after_s` 는 "느린 작업"이 아니라 **"죽은 프로세스"** 만
잡는 본래 역할로 돌아간다. 900초는 에이전트 예산 600초 + 여유다.

`step_s` 와 `stuck_after_s` 가 둘 다 900초인 것은 우연이고, 둘은 다른 축이다. `step_s` 는
`policy.TimeoutConfig` 의 엄격 증가 사슬(`tool_s < executor_s < step_s < run_s`)에 속하고
여전히 배선되지 않는다. `stuck_after_s` 는 리컨실러의 관측 파라미터로 그 사슬 밖에 있다.
`validate()` 는 둘을 비교하지 않는다.

`run_s` 배선은 SP1 스펙 §12.2 가 미뤄둔 것이다. 리컨실러가 요구사항의 `created_at` 나이를
보고 `run_s` 를 넘기면 `GIVE_UP` 한다. 실제 LLM 지연이 붙어 "느린 것"과 "멈춘 것"을 나이만으로
가르기 어려워졌으므로, 이제 요구사항 전체에 시간 예산이 필요하다.

### 9.3 재시도 분류는 건드리지 않는다

Ollama 가 모델 로딩 중 503 을 주는 경우가 있다. 지금 분류로 TRANSPORT(3회 재시도)이고 그것이
맞다. 새 실패 클래스를 만들지 않는다 — **분류 체계를 건드리지 않는 것이 SP1 회귀를 막는
길이다.** 다만 `backoff_seconds` 는 LLM 모드에서 늘린다(모델 로딩이 30초쯤 걸린다).

## 10. 실패 처리

SP1 의 실패 분류(전송·실행·독성입력 / 품질반려·정책차단)를 그대로 쓴다. SP2 가 추가하는 것은
**에이전트 내부 실패를 어느 분류에 넣는가** 뿐이다.

| 에이전트 내부 상황 | 분류 | 근거 |
|---|---|---|
| 턴 상한 초과 | EXECUTION | 같은 입력으로 다시 하면 다를 수 있다 (temperature > 0) |
| 작업 예산 초과 | EXECUTION | 위와 같다 |
| Ollama 연결 실패 | TRANSPORT | 바이트가 안 나갔다 |
| Ollama 503 (로딩 중) | TRANSPORT | 일시적 |
| 도구를 한 번도 안 부름 | EXECUTION | 근거 없는 산출물을 만들지 않는다 (§5.3) |
| MCP 서버 연결 실패 | TRANSPORT | 워크스페이스가 아직 안 떴다 |

### 10.1 멱등성 — SP1 스펙 §12.1 대응

SP1 은 "같은 멱등성 키가 에이전트에 두 번 도달하는 경로가 없다"를 전제로 에이전트측 멱등성을
구현하지 않았다. **SP2 는 그 전제를 유지한다.**

`retry.is_undelivered` 의 범위를 넓히지 않는다. 그 자리 재시도는 여전히
`ConnectError`/`ConnectTimeout` 로만 좁혀져 있고, 모호한 실패는 행을 끝내고 새 `attempt`
(= 새 키)로 다시 간다.

> **이 제약을 깨면 비용이 발생한다.** SP1 에서 중복 디스패치는 스텁을 한 번 더 부르는
> 것(0원)이었다. SP2 에서는 **LLM 을 한 번 더 도는 것**이다. 로컬 모델이라 금전 비용은
> 0원이지만 시간 비용은 5~10분이고, 외부 API 어댑터를 붙이는 순간 금전 비용이 된다.
>
> 넓혀야 한다면 에이전트가 `vsi_idempotency_key` 로 완료된 Task 를 찾아 재실행 대신 기존
> Artifact 를 반환하도록 구현하고, 그 동작을 테스트로 고정해야 한다.

## 11. 관측성

### 11.1 그래프 UI

도구 호출 이벤트(§8.1)를 받아 에이전트 노드 아래에 현재 동작을 띄운다 — "개발: `calc.py` 쓰는
중", "QA: pytest 실행 중".

**목적은 5분짜리 작업이 멈춘 게 아니라 일하는 중임을 보이는 것이다.** SP1 에서는 모든 작업이
1초 안에 끝나 필요 없던 정보다. 게이트웨이와 리듀서의 구조 변경은 없다 — 새 이벤트 타입이
하나 늘 뿐이다.

### 11.2 트레이스

LLM 호출과 MCP 호출이 각각 스팬이 된다.

| 스팬 | 속성 |
|---|---|
| `llm.chat` | `vsi.llm.model`, `vsi.llm.turn`, `vsi.llm.tool_calls` |
| `mcp.call` | `vsi.tool.name`, `vsi.tool.ok`, `vsi.tool.exit_code` |
| `agent.task` | `vsi.agent`, `vsi.revision`, `vsi.turns_used`, `vsi.budget_s` |

`agent.task` 스팬이 SP1 의 오케스트레이터 스팬 아래에 붙어 **하나의 트레이스로 전 구간이
이어진다.** MCP 호출은 HTTP 이므로 `HTTPXClientInstrumentor` 가 컨텍스트를 전파한다.

## 12. 테스트 전략

비결정적 에이전트를 테스트한다는 것은 **출력이 아니라 성질을 단언한다**는 뜻이다.

### 12.1 1층 — SP1 회귀 그물 (변경 없음)

`VSI_AGENT_MODE=stub` 에서 SP1 의 151개 테스트가 그대로 통과해야 한다. 스텁을 지우지 않는
이유가 이것이다. **SP2 의 어떤 변경도 이 층을 깨서는 안 된다.**

### 12.2 2층 — MCP 도구 서버 (완전히 결정적)

파일 연산과 서브프로세스다. 평범하게 테스트한다.

- 경로 탈출 3종(`../`, 절대경로, 심볼릭 링크)이 도구 오류로 차단되는가
- 다른 요구사항의 디렉터리에 닿을 수 있는가 (닿으면 안 된다)
- `pytest` 종료코드가 그대로 전달되는가
- 서브프로세스 타임아웃이 걸리는가
- 출력 절단이 꼬리를 남기는가

### 12.3 3층 — 가짜 LLM 으로 루프 검증 (결정적)

Ollama HTTP 호출 자리에 각본대로 `tool_calls` 를 뱉는 트랜스포트를 끼운다. 로직의 대부분이
여기서 잡힌다.

- 도구 호출 결과가 대화에 다시 들어가는가
- 12턴째에 정확히 실패로 끝나는가
- 작업 예산 초과가 EXECUTION 으로 분류되는가
- 도구 오류가 예외가 아니라 대화 메시지로 들어가는가
- 도구를 한 번도 안 부르면 실패로 끝나는가
- **`verdict` 가 도구 종료코드에서만 오는가** — 모델이 "PASS" 라고 말해도 종료코드가 1이면
  FAIL 이어야 한다

### 12.4 4층 — 실제 모델 (소수, 격리)

`@pytest.mark.llm` 으로 표시하고 CI 기본 실행에서 제외한다. 모델 출력 내용은 **절대 단언하지
않는다.** 단언하는 것은 성질이다.

- 도구 호출이 최소 1회 나왔는가
- 예산 안에 종단 상태(`accepted` 또는 `escalated`)에 도달했는가
- QA 판정이 `run_tests` 종료코드와 일치하는가
- 2회차 개발 프롬프트에 1회차 실패 출력이 실려 있는가

## 13. 완료 정의

| | 기준 | 검증 방법 |
|---|---|---|
| 1 | 요구사항 1건이 실제 LLM 으로 사람 개입 없이 종단 상태에 도달 | `@pytest.mark.llm` 통합 테스트. `accepted` 와 `escalated` 모두 성공 |
| 2 | 생성 코드가 워크스페이스를 벗어나지 못한다 | 경로 탈출 3종 차단 테스트 + `workspace` 가 internal 네트워크에만 속함을 compose 에서 확인 |
| 3 | QA·보안 판정이 도구 종료코드와 100% 일치 | 3층 테스트: 모델이 반대로 말해도 종료코드가 이긴다 |
| 4 | 환류가 실제 실패 출력에 근거한다 | 2회차 개발 프롬프트에 1회차 pytest 메시지가 포함됨을 단언 |
| 5 | SP1 테스트 151개가 스텁 모드로 전부 통과 | 커널 무회귀 |
| 6 | 외부 LLM API 호출 0회 | SP1 의 criterion-5 스캔 확장 — `api.anthropic.com`·`api.openai.com` 부재 + Ollama 만 사용 |

기준 1 이 `escalated` 를 성공으로 치는 이유는 §1 에 있다. 별도로, **`accepted` 로 완주한 실행
기록 하나를 데모로 남긴다** — 이것은 테스트가 아니라 기록이다.

## 14. SP3 로 넘기는 제약

### 14.1 동시 실행은 Ollama 가 병목이다

단일 Ollama 인스턴스가 모든 에이전트의 요청을 처리한다. QA 와 보안이 병렬 배정되므로 요구사항
하나만 돌려도 동시 요청이 2건이고, 요구사항을 여러 건 돌리면 선형으로 늘어난다.

SP2 는 동시 1~2건을 권장하되 **코드로 강제하지 않는다.** 오케스트레이터에 요구사항 큐를 넣는
것은 새 동시성 제어를 도입하는 일이고, 그 상한이 §9.2 의 시간 상한들과 어떻게 상호작용하는지
검증되지 않았다. 지금은 동시 요구사항이 늘면 에이전트 작업 예산(600초)을 넘겨 EXECUTION 실패로
나타난다 — **조용히 망가지지 않고 기존 실패 경로로 드러난다.**

`OLLAMA_NUM_PARALLEL` 조정과 요구사항 큐잉은 `vsi.task.open_age_s` 분포가 쌓인 뒤 SP3 에서
다룬다.

### 14.2 `stuck_after_s` 900초도 측정된 값이 아니다

에이전트 예산 600초 + 여유로 정한 값이다. `reconciler.force_fail` 스팬의
`vsi.task.open_age_s` 분포가 쌓이면 근거를 갖고 조정한다. SP1 §12.3 과 같은 성격의 부채다.

### 14.3 에이전트의 `/message:send` 에 인증이 없다 (⚠ 구현 시 최우선)

`agent_runtime` 은 A2A 라우트에 인증 미들웨어를 붙이지 않는다. `/message:send` 는 같은
도커 네트워크의 누구나 부를 수 있는 무인증 POST 다. 실행으로 확인했다 — `event-gateway`
에서 `dev:8000/message:send` 를 부르면 HTTP 400(페이로드 거부)이 돌아온다. 라우트 자체는
열려 있다는 뜻이다.

**SP1 부터 있던 구멍이다.** SP2 가 만든 것이 아니다. 다만 SP2 는 도달 가능한 컨테이너
집합에 `workspace` 를 더했고, 그곳이 **LLM 이 쓴 코드가 실제로 실행되는 유일한 장소**다.
`internal` 네트워크는 외부 송신을 막지만 같은 네트워크의 컨테이너끼리는 막지 않는다.

구체적 공격 경로:

1. `workspace` 에서 실행되는 코드가 `POST http://dev:8000/message:send` 를 부른다.
2. `llm_agent/executor.py` 의 `_incoming_payload` 는 `requirement_id` 키만 있으면 받아들인다.
   그 작업이 오케스트레이터가 디스패치한 것인지, 호출자가 오케스트레이터인지 검사하지 않는다.
3. 그 값이 그대로 `ToolBridge` → `workspace_root` 로 흘러 `/workspace/<requirement_id>/`
   를 만든다. **다른 요구사항의 디렉터리를 지정할 수 있다.**
4. `dev` 역할의 도구에 `write_file` 이 있으므로 읽기가 아니라 **쓰기**가 된다.
   `qa`/`security` 를 부르면 그 디렉터리에서 `run_tests`/`run_security_scan` 이 돈다.

부수 효과로 공유 Ollama 를 소모하고, `title`/`feedback` 필드로 다음 LLM 턴에 프롬프트를
주입할 수 있다.

**SP2 에서 고치지 않은 이유:** 스펙 §2 가 인증을 범위에서 제외했고, 고치려면 SP1 이 만든
A2A 라우트 계층을 건드려야 하는데 통합 테스트 144개가 그 계약이다. SP2 의 실제 위협은
적대적 공격자가 아니라 장난감 과제를 푸는 로컬 모델이며, 도달 경로도 로컬 도커 네트워크
안에 갇혀 있다.

**공개 환경에 올리는 순간 실제 취약점이 된다.** 고칠 때는 `/message:send` 에
`VSI_PUSH_TOKEN` 급 공유 비밀을 요구하고, `requirement_id` 가 실제로 열려 있는 작업과
일치하는지 `ToolBridge` 에 닿기 **전에** 검증해야 한다.

### 14.4 프롬프트는 튜닝하지 않는다

SP2 의 증명 대상은 인프라다. 프롬프트를 다듬어 성공률을 올리는 작업은 명시적으로 범위 밖이다.
성공률이 낮으면 §5.4 의 되돌림 조건을 검토하되, 프롬프트 반복 개선에 시간을 쓰지 않는다.
