SP1 상태 모델 — 두 층으로 분리

A2A Task는 한 에이전트의 1회 실행. 환류 루프는 그보다 위층입니다. 한 상태 기계로 합치면 무너집니다.

층 1 — A2A Task 상태 · a2a-sdk 소관 · 에이전트마다
층 2 — 워크플로 상태 · 우리 소관 · 요구사항 ID마다
두 층이 만나는 지점 — Task 계보
REQ-001 회원가입  workflow: accepted · revisions=2
├─ task/dev/8f1a rev 1 → completed  artifact: source_code@v1
├─ task/qa/3c02 → completed  verdict: FAIL 중복 가입 미처리
├─ task/sec/9d77 → completed  verdict: FAIL 평문 비밀번호 저장
├─ task/dev/b204 rev 2  revision_of: 8f1a → completed source_code@v2
├─ task/qa/f5e1 → completed  verdict: PASS
└─ task/sec/1a93 → completed  verdict: PASS

Task는 불변, 시도마다 새로 만듭니다. revision_of로 계보만 잇습니다. 실패한 시도가 지워지지 않으므로 SP3 비교실험에서 "몇 번 만에 수렴했나"를 COUNT(*) 한 줄로 셀 수 있고, 시각화 B에서는 새 Task마다 새 엣지가 그려져 환류가 눈에 보입니다.

이 모델이 푸는 문제

분리해서 얻는 것

  • failed(인프라 장애 → 재시도)와 verdict: FAIL(품질 반려 → 환류)이 다른 층에 있어 섞이지 않습니다. 에이전트가 죽은 것과 코드가 틀린 것은 대응이 정반대입니다.
  • input-required를 재작업이 아니라 사람 승인 전용으로 씁니다 — 배포·결제·개인정보는 사람 승인이라는 안전성 요구와 정확히 맞물립니다.
  • 반복 상한이 워크플로 층에 있어 에이전트가 우회할 수 없습니다.

대가로 감수하는 것

  • Task 행이 많아집니다 (수렴까지 요구사항당 6~10개). 인덱스 설계가 필요합니다.
  • SP2에서 dev 에이전트가 이전 시도 맥락을 자동으로 못 가집니다 — 이전 코드와 리포트를 입력 Artifact로 명시적으로 넣어줘야 합니다. 대신 토큰 사용량이 명시적으로 드러나서 측정이 정직해집니다.
  • 계보를 따라가야 "이 요구사항이 몇 번 돌았나"를 알 수 있습니다 (조회 한 번 더).
