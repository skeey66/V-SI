# SP1 구현 중 계획과 달라진 결정들

계획과 스펙이 답하지 않았거나, 구현하면서 계획이 틀렸다고 판단해 바꾼 지점을 모았다.

각 항목은 **무엇을 정했는가 / 왜 / 틀렸을 때 무엇을 잃는가**로 적었다. 동의하지 않는
결정은 되돌리면 된다 — 되돌리는 비용도 함께 적었다.

구속력 순서: 스펙이 최종 권위, 계획은 스펙을 향한 논증, 아래 결정은 둘 다 답하지 않은 것을 정한다.

---

## A. 계획 결함을 고친 것 (계획이 틀렸다고 판정)

### A-1. 멱등성 키를 netstring 인코딩으로 교체 (Task 3)

계획이 지시한 `"|".join([...])`은 필드 경계가 모호해
`(requirement_id="A", agent="B|1|C")`와 `(requirement_id="A|B", agent="1|C")`가
같은 키를 만든다. 이 키는 UNIQUE 컬럼이라 충돌 시 정당한 작업이 중복으로 오인돼 거부된다.

SP1에서는 도달 불가능하다 — agent가 닫힌 집합이고 requirement_id도 우리가 만든다.
**SP2에서 기획 에이전트(LLM)가 requirement_id를 생성하는 순간 도달 가능해진다.**
길이 접두(netstring)로 교체했다.

*틀렸을 때 비용:* 거의 없음. 키 형식이 바뀌지만 저장된 키가 아직 없었다.

### A-2. `test_card_carries_no_secret`을 고침 — 테스트가 틀렸다 (Task 5)

계획의 테스트가 금지 문자열에 `api_key`를 넣었는데, protobuf 텍스트 직렬화는
oneof 필드명(`api_key_security_scheme`)을 포함한다. 그래서 **의미상 올바른**
`APIKeySecurityScheme`을 쓰면 테스트가 깨진다.

구현자는 통과시키려고 `HTTPAuthSecurityScheme.scheme`(RFC 7235의 Bearer/Basic 슬롯)에
커스텀 헤더명을 넣는 우회를 택했고 — 그리고 그 사실을 정직하게 보고했다.
필드명 노출은 시크릿 유출이 아니라 인증 *방식* 선언이고 스펙이 카드에 넣으라 한 바로 그것이다.
테스트를 버리고 스킴을 되돌렸다.

*틀렸을 때 비용:* 카드의 보안 스킴 선언 형태가 바뀌어 인증 배선 재조정. 몇 줄.

### A-3. `test_verdict_sequence_repeats_last_when_exhausted`를 강화 (Task 6)

계획의 테스트는 소진 후 `next_verdict()`를 **한 번만** 호출해 "PASS"인지 본다.
그런데 "PASS"는 원래 리스트의 마지막 값이기도 해서, "마지막 값을 한 번 주고 그 뒤엔 아무거나"
하는 구현도 통과한다. `never_passes.yaml`은 `verdicts:[FAIL]` 하나로 3회 환류를 돌리므로
**무한 반복 동작에 실제로 의존한다.** 여러 번 호출해 전부 같은 값인지 보도록 고쳤다.

*틀렸을 때 비용:* 없음. 테스트만 강해지고 구현은 이미 올발랐다.

### A-4. Task 11의 시나리오를 분리 (`verdicts_fail_twice.yaml` 신설)

계획의 Task 11 테스트는 `qa_fails_twice.yaml`을 쓰는데, 그 시나리오의
`dev: attempt_2: crash`는 **재시도 픽스처**라 Task 12 없이는 rev-2 dev 태스크가 멈춰
`accepted`에 도달하지 못한다(구현자가 3회 재현). 크래시 없는 동일 verdict 시퀀스로
환류를 검증하고 `qa_fails_twice.yaml`은 Task 12용으로 남겼다.

부수 효과로 "dev 태스크 3개" 계보 단언이 Task 12가 재시도를 추가한 뒤에도 유효하게 유지된다.

*틀렸을 때 비용:* 시나리오 파일 하나 추가. 거의 없음.

### A-5. `published_at is None` 단언을 교체 (Task 17)

오케스트레이터의 계약은 "전이마다 아웃박스 행 1개를 미발행 상태로 쓴다"이고,
그것이 **계속** 미발행인지는 게이트웨이 소관이다. 게이트웨이는 전역 방송하므로
이 단언은 WS 클라이언트가 하나도 없을 때만 통과한다 — 브라우저를 열면 깨진다
(실제로 열려 있던 Chrome 탭 때문에 깨졌고 `lsof`로 확인했다).

이벤트 **시퀀스**를 단언하도록 바꾸고, 쓰기측 기본값은 격리된 단위 테스트로 옮겼다.

*틀렸을 때 비용:* 없음. 테스트가 경합에서 벗어났다.

## B. 계획이 정의하지 않은 것을 정한 것

### B-1. 시나리오의 `attempt_N`은 스텁 자신의 에이전트별 호출 순번이다 (Task 7)

계획이 정의하지 않아 구현자가 `context.metadata` 임시 가정을 넣었다.
"오케스트레이터 재시도 횟수"로 읽으면 `dev: {attempt_2: crash}`는 **발동 불가능한 죽은 설정**이
된다 — 시도 2는 시도 1 실패 시에만 생기는데 시도 1엔 크래시가 없다.
호출 순번으로 읽으면 dev 1회차(rev1) 성공 → 2회차(rev2) 크래시 → 재시도 → 3회차 성공으로
전부 성립한다. 스텁이 카운터를 소유하므로 자기완결적이고 결정적이다.

*틀렸을 때 비용:* 크래시 주입이 안 걸리면 재조정. 스텁 내부 몇 줄.

### B-2. Task 13을 Task 12보다 먼저 실행 — 계획 순서를 뒤집음

구현자의 측정: **SDK는 executor 오류 경로에서 푸시를 보내지 않는다**(크래시한 태스크는
4개가 아닌 2개 푸시만). 따라서 에이전트 내부 크래시는 푸시 트리거가 없고,
Task 12의 통합 테스트는 stale `working` 행을 폴링하는 **Task 13 리컨실러 없이는 성립하지 않는다.**
반대로 리컨실러는 Task 12 없이도 동작한다.

*틀렸을 때 비용:* 다시 뒤집으면 됨. 순서만 바뀐다.

### B-3. 게이트웨이를 at-least-once 전달로 전환 (Task 15)

계획은 발행 표시 후 전송이었다. 크래시가 그 사이에 나면 **이벤트가 유실된다.**
전송 후 표시로 뒤집으면 크래시 시 재전달되는데, UI 그래프의 중복 이벤트는 무해하고
유실은 무해하지 않다. 이 태스크의 존재 이유가 게이트웨이 죽음을 견디는 것이다.

*틀렸을 때 비용:* 클라이언트가 `event_id`로 중복 제거를 해야 함 — Task 16 요구사항으로 실었다.

## C. 내가 틀렸다가 고친 것

### C-1. Task 13 에서 기록한 remediate 안전성 논거가 틀렸다

나는 "경쟁에서 진 호출자는 dispatch 전에 `IllegalTransition`으로 죽는다"고 기록했는데,
`(IMPLEMENTING, DEV_DONE) → VERIFYING`는 전이 테이블상 **합법**이라 죽지 않고 전이한다.
결과: revision R+1에 dev 행 2개, 검증자 행 0개, state=verifying.
staleness 게이트(5s) 덕에 도달성은 낮았지만 근거가 거짓이었으므로
`expected=REMEDIATING`을 넣고 False면 dispatch를 건너뛰게 했다.

최종 리뷰가 이것을 잡아냈고, 재리뷰가 가드 없이 테스트가 실제로 RED인지 확인했다.

*틀렸을 때 비용:* 없음. 한 키워드.

## D. 코드 대신 스펙을 고친 것

### D-1. 멱등성은 스펙을 수정해 해결한다. 코드를 바꾸지 않는다

스펙 §8은 "에이전트가 같은 키로 완료된 Task가 있으면 재실행하지 않고 기존 Artifact를
반환한다"고 요구했다. 그런데 Task 12가 제자리 재제출을 `is_undelivered`
(ConnectError/ConnectTimeout)로 좁힌 뒤로는 **같은 키가 에이전트에 두 번 도달하는
정당한 경로가 없다.** 애매한 실패는 행을 실패시키고 리컨실러가 새 attempt(=새 키)로
재디스패치한다. 요구사항이 불필요해진 것이다.

구현 대신 스펙을 현실에 맞게 고쳤다. 다만 **되돌림 조건을 명시했다** — 제자리 재시도
범위가 다시 넓어지면 에이전트측 멱등성이 필수다. 경고를 스펙 §8·§12.1과
`idempotency.py`/`scenario.py` docstring 네 곳에 남겼다.

*틀렸을 때 비용:* SP2에서 재시도 정책을 바꿀 때 이 경고를 못 보면 중복 LLM 과금.
경고를 네 곳에 중복해 완화했다.

### D-2. `run_s` 타임아웃을 배선하지 않고 문서화만 함

A2 수정 후 모든 태스크 행은 verdict 보유 / 미결(정체 천장 60s) / 실패(재시도 상한)
셋 중 하나다 — 비종단 클래스 전부가 기존 두 천장으로 덮인다. 시간 축 규칙을 하나 더 두면
새 종단 경로가 생기는데 `give_up`·환류 상한과의 상호작용이 검증되지 않는다.

*틀렸을 때 비용:* 전체 실행 시간 상한이 없다. 개별 천장들이 유한하므로 총합도 유한하지만
상한이 명시적이지 않다. `policy.py`에 이미 값이 있으니 배선은 몇 줄.

## E. 환경에 손댄 것

### E-1. Docker postgres를 호스트 포트 55432로 이동

사용자의 Homebrew `postgresql@17`이 5432를 점유해 localhost 연결이 로컬 DB로 샜다.
구현자는 **로컬 서비스를 껐다 켜는 우회**를 썼는데, 그 DB는 사용자가 실습(skala_db)에
쓰는 것이라 반복하면 안 된다. 컨테이너 내부 주소(`postgres:5432`)는 그대로 두고
호스트 매핑과 테스트 URL만 바꿨다.

*틀렸을 때 비용:* 55432도 점유돼 있으면 한 번 더 이동. 2줄.

### E-2. pytest에 `pythonpath = ["packages"]` 추가

editable 설치의 `.pth` 파일이 macOS UF_HIDDEN 플래그로 간헐 무시돼 `ModuleNotFoundError`가 났다.
`pythonpath`를 직접 주면 `.pth` 의존이 사라져 실패 모드 자체가 없어진다.

*틀렸을 때 비용:* 없음. editable 설치도 그대로 둬서 둘 다 동작한다.

### E-3. Docker Desktop을 직접 기동

Task 4 이후 전부 `docker compose` 의존인데 데몬이 꺼져 있었다.
로컬·가역적이고 의뢰받은 작업의 전제조건이라 중단하지 않았다.

*틀렸을 때 비용:* Docker Desktop이 리소스를 점유. 종료하면 됨.

## F. 보류한 것 (알면서 안 고친 것)

수정 웨이브는 1회뿐이라는 규칙에 따라, 최종 재리뷰가 새로 찾은 Minor는 고치지 않고 기록했다.

### F-1. `tests/stub_agent/test_scenario.py`의 상대경로 glob

`Path("scenarios")`를 glob한다. CI·로컬 모두 pytest를 리포 루트에서 돌리고 `testpaths`가
이를 고정하므로 현재는 공허 통과가 나지 않는다.

*틀렸을 때 비용:* 다른 cwd에서 돌리면 이 회귀 테스트 1건이 조용히 아무것도 검증하지 않는다.
수정은 `REPO_ROOT / "scenarios"` 한 줄. **SP2 착수 시 1순위 정리 대상.**

### F-2. `scenario._parse_failures`의 비문자열 YAML 키

`2: crash` 같은 키에서 `ScenarioError` 대신 `AttributeError`가 난다.
잘못된 시나리오는 어느 쪽이든 기동 시 죽고, 배포된 다섯 시나리오는 전부 문자열 키다.

*틀렸을 때 비용:* 오타 시 친절한 메시지 대신 스택트레이스. 진단 품질 저하일 뿐 동작 결함 아님.

### F-3. `POST /requirements`가 202를 주면서 동기로 실행

`start`가 기획 에이전트 디스패치까지 동기로 돈다. 202 Accepted의 의미와 어긋난다.
최초 리뷰부터 Minor로 유예됐다.

*틀렸을 때 비용:* 요청이 기획 디스패치 시간만큼 블록된다. 스텁에서는 무시할 수준,
SP2에서 실제 LLM이 붙으면 눈에 띈다.

### F-4. 계획 문서를 다시 쓰지 않음

`docs/plans/2026-09-17-sp1-a2a-kernel.md`는 여전히 삭제된
`record_call`/`DuplicateCallError`/`PIPELINE`을 명세한다. 계획은 **그 시점의 논증 기록**이고
스펙이 최종 권위이므로, 사후 편집해 실제 실행 경로를 지우지 않기로 했다.
차이는 위 A·B·D 항목이 설명한다.

*틀렸을 때 비용:* 계획만 읽은 사람이 존재하지 않는 심볼을 찾는다.
계획 헤더가 스펙을 가리키고 스펙은 정확하다.
