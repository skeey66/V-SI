# SP2 구현 중 계획과 달라진 결정들

초기 설계와 스펙이 답하지 않았거나, 구현하면서 초기 설계가 틀렸다고 판단해 바꾼 지점을 모았다.

각 항목은 **무엇을 정했는가 / 왜 / 틀렸을 때 무엇을 잃는가**로 적었다. 동의하지 않는
결정은 되돌리면 된다 — 되돌리는 비용도 함께 적었다.

구속력 순서: 스펙이 최종 권위이고, 아래 결정은 스펙이 답하지 않은 것을 정한다.
SP1의 같은 문서는 [`2026-09-17-sp1-rulings.md`](2026-09-17-sp1-rulings.md)에 있다.

---

## A. 초기 설계가 틀렸다고 판정한 것

### A-1. 경로 봉쇄의 두 구멍

초기 설계의 정규식 `^[A-Za-z0-9._-]+$`가 `"."`을 전체 일치로 통과시킨다. 그러면
`workspace_root(base, ".")`가 **base 자체를 요구사항 루트로 반환**한다. 리뷰에서 재현했다 —
그 루트로 다른 요구사항의 파일을 읽어냈다. SP2의 유일한 보안 경계가 무너지는 경로였다.

함께 나온 것: macOS 대소문자 무시 파일시스템에서 `REQ-1`과 `req-1`이 같은 inode를 가리킨다.

대소문자 정책은 **정규화가 아니라 충돌 거부**로 정했다. 소문자화하면 서로 다른 두 요구사항
(DB에서 별개 PK)이 한 워크스페이스를 공유하게 되어 같은 격리 실패가 이름만 바꿔 남는다.

*틀렸을 때 비용:* 거의 없음. 검증 로직 몇 줄과 회귀 테스트 2건.

### A-2. MCP 권한 집행을 헤더가 아니라 경로 분리로 (MCP 서버)

초기 설계는 `X-VSI-Agent` 헤더로 역할을 판별하는 것이었는데, 정작 `TOOLS_BY_ROLE`을
순수 함수로만 두고 디스패치에 연결하지 않았다. 주석은 "서버 쪽의 독립된 집행 기준"이라
주장하는데 코드가 구현하지 않는 상태였다.

고치면서 **원래 논거도 정정했다.** "에이전트가 보내는 값이 곧 권한이 된다"고 적었는데
절반만 맞다 — 이 홉에 인증이 없으므로 헤더든 경로든 악의적 컨테이너는 어느 역할이든
사칭한다. 실제로 사주는 건 **버그 방어**다.

그 목적에는 역할별 MCP 서버를 `/mcp/{role}/`로 따로 마운트하는 쪽이 맞다. dev가
`run_tests`를 못 부르는 이유가 "검사해서 막아서"가 아니라 **"그 경로에 그 도구가 존재하지
않아서"**가 된다.

*틀렸을 때 비용:* MCP URL에 역할이 들어가 에이전트별 설정이 달라진다. compose가 이미
에이전트별 환경변수를 주므로 추가 비용은 거의 없다.

### A-3. 대화 루프에 초기 설계에 없던 요구사항 셋

초기 설계를 다시 확인해 보니 `run_loop`에 `bridge.call`을 감싸는 예외 처리가
**어디에도 없다.** 그런데 브리지는 허용 목록 밖 이름에 예외를 던진다. 두 경로가 들어온다:
깨진 도구 호출 센티널, 그리고 모델이 정상 형식으로 없는 도구를 부르는 경우. 둘 다
에이전트 턴을 죽인다.

함께 실은 것: Ollama 503 재시도(아래 C-1), 그리고 긴 호출에서 예산 검사가 무너지는 문제.

*틀렸을 때 비용:* 없음. 이 구멍은 실제 모델을 붙여야 드러나는 종류라 미리 막는 게 싸다.

### A-4. `run_s` 검사 위치 (run_s backstop)

초기 설계는 이 검사를 "함수 맨 앞, 다른 어떤 판단보다 먼저" 두도록 했다. 그 결과 마지막
검증자가 이미 PASS를 쓴 요구사항이 나이 한 틱 때문에 버려진다. **다 끝난 일을 시간
초과로 폐기하는 것**이고 로그에서 "진짜 멈춤"과 구별되지 않는다.

원칙을 다시 썼다: **예산은 새 작업을 막는 것이지 끝난 작업을 버리는 것이 아니다.**
FINISH를 앞에 두고, `run_s`는 디스패치·환류·탐색만 선점한다.

*틀렸을 때 비용:* 예산을 넘긴 요구사항이 최대 한 틱(2초) 더 살아 완주한다. 그게 낫다.

## B. 초기 설계가 정의하지 않은 것을 정한 것

### B-1. 권한 표 이중 정의를 유지 (MCP 서버 ↔ 역할 정의)

`TOOLS_BY_ROLE`(서버)과 `Role.tools`(에이전트)가 같은 값을 두 곳에 둔다. DRY 위반 지적이
나오면 기각하기로 미리 정했다.

역할별 서버 분리 이후 이 판단은 더 강해졌다 — 두 표는 독립된 집행 지점이지 중복이 아니다.
DRY 반론은 영구 기각한다.

*틀렸을 때 비용:* 권한을 바꿀 때 두 곳을 고쳐야 한다. 양쪽 테스트가 잡으므로 조용히
어긋나지는 않는다.

### B-2. 자문 이벤트를 `await`하되 실패는 삼킨다 (자문 이벤트 · LlmExecutor)

`create_task`로 띄우면 참조가 GC되어 이벤트가 유실된다. `await`가 맞다.

그런데 무방비로 await하면 **Postgres 한 번 끊김이 에이전트 실행 전체를 죽인다.**
스펙이 "워크플로 권위 없음"이라 선언한 이벤트가 워크플로 작업을 실패시키는 셈이다.
`await`는 유지하되 실패는 로그로 삼킨다.

가드 위치는 `loop.py`가 아니라 `executor.py`다 — 루프의 계약은 범용으로 두고, "이 콜백은
워크플로 권위가 없다"는 지식은 콜백을 만드는 쪽에 둔다.

*틀렸을 때 비용:* 이벤트 쓰기 실패가 조용해진다. 로그로 남고, UI 표시가 빠지는 것과
에이전트 작업이 죽는 것 중에는 전자가 낫다.

### B-3. run_s backstop과 상한 값 조정을 한 변경으로 묶음

둘 다 `reconciler.py`의 시간 상한이고 **두 값이 서로를 전제한다** — 에이전트 예산 600초
< `stuck_after_s` 900초 < `run_s` 3600초. 따로 고치면 부등식이 깨진 중간 상태가 커밋되고
리뷰에서도 각 숫자를 다른 diff에서 보게 된다.

*틀렸을 때 비용:* diff가 조금 커진다. 둘 다 상수와 배선이라 리뷰 부담은 작다.

## C. 스펙이 틀렸다고 판정한 것

### C-1. "Ollama 503 → TRANSPORT"는 구현 불가능하다 (스펙 §10)

스펙에 적었던 행인데, 직접 확인해보니 **불가능하다.**

`TERMINAL_TASK_STATES`에 `TASK_STATE_ERROR`가 없다. 에이전트에서 예외가 올라가면 SDK가
ERROR로 표시해도 오케스트레이터는 종단으로 인정하지 않고, `stuck_after_s`(900초)에 걸려
EXECUTION으로 강제 실패한다. 더 근본적으로 **파이썬 예외 타입은 A2A 와이어를 건너지
않는다** — `classify()`에 케이스를 추가해도 오케스트레이터는 그 예외를 볼 일이 없다.

재시도를 **에이전트 안으로** 옮겼다. 모델 로딩은 30초면 끝나는 국소적·일시적 조건이고,
에이전트의 600초 예산 안에서 백오프로 흡수된다.

`TASK_STATE_FAILED`로 바꿔 올리는 방법은 안 썼다 — SP1이 이미 그 상태를 "검증자 FAIL
판정"에 쓰고 있어, 섞으면 QA 반려와 모델 미기동을 구분 못 하게 된다.

*틀렸을 때 비용:* Ollama가 영구히 죽어 있으면 여전히 900초 뒤 FORCE_FAIL이다. 전부 죽은
상황이라 감내 가능하다.

### C-2. `/message:send` 무인증을 SP3로 미룬다 (스펙 §14.3 신설)

workspace 네트워크 격리를 넣으면서 "현재는 무해하다"고 판단했는데, 틀렸다. `internal`
네트워크는 외부 송신만 막고 같은 네트워크 컨테이너끼리는 안 막는다. `workspace`에서
에이전트의 `/message:send`를 인증 없이 부를 수 있고, `requirement_id`를 검사하지 않으므로
남의 요구사항 디렉터리에 `write_file`이 된다.

**실행으로 범위를 재확인했다:** `event-gateway`에서도 HTTP 400으로 도달한다 —
라우트는 열려 있다. **SP1부터 있던 구멍**이고 SP2는 도달 가능한 집합에 `workspace`를
더했을 뿐이다. 다만 그 하나가 LLM이 쓴 코드가 도는 유일한 장소다.

구현하지 않은 이유: 스펙 §2가 인증을 범위에서 뺐고, 고치려면 SP1의 A2A 라우트 계층을
건드려야 하는데 통합 테스트 144개가 그 계약이다. 대신 **스펙 §14.3에 공격 경로를 단계별로
적어** 다음 사람이 축소 해석하지 못하게 했다.

덧붙일 점 — 완화책의 싼 절반(에이전트가 `requirement_id`를 자기가 디스패치받은 작업과
대조)은 A2A 라우트 계층을 건드리지 않는 국소 변경이고, 그것만으로도 "남의 워크스페이스에
쓰기"는 막힌다. SP3 크기로 잡은 건 과대평가다.

*틀렸을 때 비용:* 공개 환경에 올리면 실제 취약점이다. 로컬 데모에서는 도달 경로가 도커
네트워크 안에 갇힌다.

## D. 검증 방식에 관한 판단

### D-1. 통합 테스트 전에 실제 모델로 연기 테스트를 돌렸다

실제 모델 통합 테스트를 쓰기 전에 실제 모델로 스택을 한 번 돌려 봤고, 네 가지 결함이
나왔다. **넷 다 가짜 LLM 테스트에는 보이지 않았으며 하나도 모델 탓이 아니었다:**

1. MCP SDK의 DNS 리바인딩 방어가 도커 서비스명을 거부해 `initialize`가 421 — 에이전트 전멸
2. 보안 에이전트가 판정 도구를 한 번도 안 부름 (코드를 보지도 않고 답함)
3. `pytest`가 `dev` extra에만 있어 워크스페이스 이미지에 없음 — QA가 매번 FAIL
4. bandit이 기획이 쓴 인수 테스트의 `assert`를 잡음 — 보안이 영원히 FAIL

3·4번은 **테스트가 전부 초록인데 모든 실행이 반드시 실패하는** 종류였다.

이런 즉석 수정은 스펙 대조를 따로 거치지 않으므로, 머지 전에 스펙 정합성 관점에서
한 번 더 읽었다. 거기서 README의 테스트 수 오기 같은 것이 잡혔다.

*틀렸을 때 비용:* 스펙 대조를 늦게 거친 수정이 남는다. 머지 전 점검으로 완화했다.

### D-2. 선택적 강화를 하지 않았다

"비검증자에게 `not files`를 실패로" 하자는 제안이 있었다. "도구를 불렀지만 아무것도 안
만든" 경우가 여전히 성공으로 기록되기 때문이다.

하지 않은 이유: 스펙 §10의 실패 행이 "도구를 한 번도 안 부름"이라 현재 구현이 문자
그대로 부합하고, 빈 워크스페이스에서 pytest가 exit 5를 내므로 그런 실행은 `accepted`에
도달하지 못한다(백스톱임을 확인). 그리고 머지 직전이라 검증 없이 들어가는 동작 변경이
된다.

*틀렸을 때 비용:* 개발이 `list_files`만 부르고 끝낸 회차가 "빈 산출물 성공"으로 기록된다.
QA가 다음 단계에서 반드시 FAIL을 내므로 환류로 흡수되고, 요구사항 수준에서는 조용히
넘어가지 않는다.

## E. 보류한 것 (알면서 안 고친 것)

머지 전 점검에서 보류 Minor 20건을 분류했다. **머지 전 수정 3건은 전부 처리했다** — MCP
connect 타임아웃, MCP URL 조합 테스트, 비용 스캔 범위 확대.

남은 17건 중 눈여겨볼 것:

- **`stale_after_s`가 5초 그대로다.** SP1에서는 작업이 1초에 끝나 죽은 코드에 가까웠는데,
  SP2의 600초짜리 작업에서는 **작업당 약 300회 탐색**이 돈다. `probe_repetition` 신호가
  정상 작업에서도 수백이 되어 `a2a-sdk` 상류 버그를 드러내려던 목적을 잃었다. 다음에
  성능 문제로 먼저 드러날 항목이다.
- **`tool_called` 이벤트가 구현되지 않았다.** 스펙 §8.1은 둘을 정의했는데 `tool_result`만
  있다. UI가 도구 **시작**이 아니라 **완료** 시점에만 갱신되므로, 60초짜리 `run_tests`
  동안 화면이 멈춘 것처럼 보인다.
- **`run_scenario`와 `run_scenario_live`가 28줄을 복제한다.** LLM 테스트는 드물게 돌아서
  어긋나도 오래 안 드러난다.
- **비용 스캔이 여전히 `.env`와 CI 워크플로 일부를 못 덮는다** (주요 파일은 이번에 추가됨).
